# React fallback: @require Torn's own react-dom build, not fetch+eval it ourselves

[[Page React]] (`src/shims/react.ts`, `src/shims/react-dom.ts`) borrows `unsafeWindow.React`/`.ReactDOM` instead of bundling `react`/`react-dom` into the `.user.js`, saving ~500KB+ of shipped code. On at least one Safari/Tampermonkey configuration this is permanently broken (every load, not a timing race): `unsafeWindow` resolves to a genuinely separate realm, and `.React`/`.ReactDOM` are `undefined` on it — that userscript manager's isolated sandbox doesn't bridge arbitrary page-realm JS *objects*, even though plain DOM access (`document.scripts` etc.) stays reliable.

This is a preemptive port, not a reaction to a TWSE bug report: TWSE hasn't seen this failure itself, but the underlying cause is a property of the userscript-manager sandbox, not of any particular script's code, and [FFScouter](https://github.com/xentac/FFScouter) (same author, same `unsafeWindow.React`-borrowing pattern, same Safari/Tampermonkey environment) already hit it in the field. Rather than wait for a TWSE-specific report, we're carrying the same fix over ahead of time.

The diagnostic work behind this decision — the Chrome CSP finding and the Safari realm finding described below — was done in FFScouter, not independently re-verified in TWSE. It's carried over as-is because the failure lives in the userscript-manager sandbox both scripts run inside of, not in either script's own code; there was nothing TWSE-specific to test.

We first tried fetching Torn's own `react-dom` UMD build (`torn.com/builds/react-umd/react-dom.<version>.<hash>.production.js` — React itself is bundled inside it as an internal webpack module) via `GM_xmlhttpRequest` and running it with `new Function(...)` in our own realm, discovering the exact URL at runtime by scanning `document.scripts`. A standalone diagnostic userscript (built and run against the reporting user's machine, in FFScouter) proved this doesn't work, in two independent ways on two different engines:

- **Chrome**: `new Function(...)` throws `EvalError: ... 'unsafe-eval' is not an allowed source of script`. Torn's CSP `script-src` includes `'unsafe-eval'` on some page loads but not others (the directive is dominated by ad/tracking-network domains, so it's plausibly tied to which third-party ad SDK is active on that particular route) — confirmed by capturing two `content-security-policy` headers from the same site, one with and one without `'unsafe-eval'`. There's no nonce/hash workaround: CSP nonces and hashes only ever authorize `<script>` *elements*, never bare `eval()`/`new Function()` calls, which are gated solely by the `'unsafe-eval'` keyword.
- **Safari**: the diagnostic's fetch-and-eval test reported `evalOk: true` (no CSP block) but `window.React`/`.ReactDOM` were still `undefined` immediately afterward, read from the same script that ran the eval. The dynamically-evaluated code's `self`/`globalThis`/`window` resolution landed somewhere other than the realm the script observes as `window` — an engine-specific quirk in how Safari's userscript sandbox implements `new Function`, not something we can rely on.

Two different engines, two different failure modes, same underlying problem: `eval`/`new Function` execution semantics aren't well-defined enough across userscript-manager sandboxes to build on.

**Decision**: use `@require` instead. It's a standard userscript metadata directive (`vite.config.ts`'s `userscript.require`) that has one well-defined guarantee across Tampermonkey/Violentmonkey: the required script's source is run in the *same realm* as the main script, before any of the main script's own code — no ambiguity about which `window` receives the result, no page-CSP dependency (the userscript manager fetches and injects it directly, the same privileged path that delivers the main script itself, not a page-context network request or `eval`). We point it at the exact same Torn `react-dom` UMD URL rather than building or hosting our own copy, so the fallback always matches whatever React version Torn's own page runs. That URL has no version-controlled path we own — the hash is Torn's own build artifact name and changes on their deploys — so it needs manual bumping in `vite.config.ts` when the fallback stops working (check a Torn page's `<script src>` tags matching `/builds/react-umd/react-dom.*.production.js` for the current one). This URL was confirmed present on Torn profile pages (via FFScouter); it has not yet been independently confirmed on `factions.php`, the only page TWSE runs on — see the `TODO` comment in `vite.config.ts`.

Because `@require` runs before any of our own module code, `getReact()`/`getReactDOM()` (`src/shims/react-loader.ts`) stay fully synchronous: prefer `unsafeWindow.React`/`.ReactDOM` when both are present, otherwise read the same-realm globals the `@require`d bundle already set by the time our code runs. No async gate, no memoized fetch state, no mount call site needs to change. React and ReactDOM are treated as an all-or-nothing pair — if only one of the two is present on `unsafeWindow`, both fall back together — so a page-realm React is never paired with a required-realm ReactDOM (or vice versa), which would break internal hook/dispatcher matching between mismatched copies.

Torn PDA doesn't support `@require` at all — its script loader just ignores the directive, which is fine, since PDA already runs unsandboxed (`unsafeWindow` is literally `window` there, per `src/utils/logger.ts` and `src/utils/api.ts`'s existing PDA handling) and has never hit this bug.

`twseconfig.debug_force_react_fallback` (Settings > "Force React fallback") forces every mount through the `@require`d fallback even when `unsafeWindow` already works, so it can be exercised on Chrome/Firefox — where it's normally never triggered — ahead of a Safari-specific release. On PDA, forcing it is a no-op rather than a real test of the fallback path: `requiredReact()` (`src/shims/react-loader.ts`) reads `globalThis.React`/`.ReactDOM`, and since `unsafeWindow === window === globalThis` on PDA, that's the exact same property Torn's page already set — indistinguishable from the un-forced path. The `@require`d bundle doesn't even need to have loaded (and, per above, never does on PDA) for this to work.

## Considered Options

- **Bundle `react`/`react-dom` into the userscript directly**: rejected — `react-dom/client`'s production build alone is ~536KB minified; would roughly double/triple the shipped bundle for every user to fix a problem only some Safari users hit.
- **Force `sandbox: 'raw'` (whole script executes in the page's real JS context)**: rejected — collapses the isolation boundary for `GM_xmlhttpRequest`, config storage, and everything else, not just React. Torn PDA already runs this way (no sandbox at all) and demonstrates the hazard class directly: FFScouter's `customElements.define(...)` at module top level threw `NotSupportedError` on reinjection there, because there's no fresh isolated realm to hide a rerun behind — the same hazard class TWSE's own `customElements.get("twse-settings-panel")` guard (`src/ui/settings-panel.tsx`) exists to avoid.
- **Dual-context bridge** (inject only the React-consuming render layer into the page via a `<script>` tag, talk to the sandboxed side over `CustomEvent`s): rejected — technically viable (Torn's CSP requires a nonce for inline scripts, but the nonce is readable off any of Torn's own already-rendered `<script nonce>` tags) but requires rebuilding every React-consuming component to route props and callbacks through a serializable event protocol, since functions can't reliably cross the isolation boundary. Disproportionate for one component (`settings-panel.tsx`).
- **Fetch-and-`eval` Torn's UMD build ourselves** (the first attempt): rejected — see above. Not fixable without either giving up on same-realm execution (defeating the point) or depending on a CSP grant that's confirmed to vary per load.
- **Build our own React 19 UMD bundle and host it (CDN or self-hosted)**: viable in principle — React 18+ dropped official UMD builds from npm, so this would've meant building and hosting a custom one, which is exactly what `@require`ing Torn's own equivalent file gets for free, with guaranteed version parity to the page and no separate hosting/build step to maintain.
- **React 17's official unpkg/jsdelivr UMD build**: rejected — no `createRoot` (introduced in React 18), and this codebase's mount call sites all use `createRoot`.

## Consequences

- The `@require`d bundle runs on every `factions.php` page load for every user, not just when Settings is opened or the fallback is needed (there's no way to make `@require` conditional) — a small extra parse/execute cost for everyone, accepted as worthwhile even though `settings-panel.tsx` is currently the only React component depending on it: the Lit→React migration is likely to add more consumers of [[Page React]] over time, and the `@require` cost doesn't scale with how many components use it.
- The exact `@require` URL is a manual-maintenance liability: it will silently go stale whenever Torn redeploys their react-dom build, until someone notices and updates `vite.config.ts`. It is also, as of this writing, unverified against `factions.php` specifically (see the `TODO` in `vite.config.ts`) — inherited from FFScouter's profile-page confirmation, not independently checked here.
